## 12 改成 6 的语义

`cubence_tools.py` 截取的是 `history[-max(1,max_context_messages//2):]`；history 每项都是一次完整 response output 加对应 `function_call_output`。

- 12 表示保留最近 6 个完整工具回合；6 表示最近 3 个。
- 不从扁平消息序列中间切断工具调用。实际 `run_episode` 的 CPU fake-client 检查确认，两种长度均保留 function_call、匹配 call_id 的 output 及同组 reasoning item。没有读取或保存模型私有 reasoning 内容。
- 每个请求重新发送 Task 文本、完整固定 system prompt、tool schema、当前 public observation 和当前双图。33 份真实 public 输入均保留 task_language、A1、目标座 ID、双相机 K/extrinsic/时间戳及图像变换；这些不会随历史裁剪消失。
- 较早的动作和回执确实会被遗忘，可能改变行为、重试次数和完整任务所需决策数。CPU 检查不证明服务端接受、策略质量或实际 6 上下文费用。

## 费用投影

用 GPT02 实际输入 token 与已保留回合数拟合，每增加一个回合约增加 1209 输入 token。假设输出长度、当前图像和工具回执分布不变，6 上下文稳态估约 **$0.083513/决策**。这不是实际请求或精确 tokenizer 结果；trace 没有保存完整隐藏 response item，无法重建全部真实请求字节。

若还要一条完整 debug 加正式 5 条，共 6 次：

- 每次 40 决策：12 上下文估 $27.23；6 上下文估 **$19.61**。
- 每次 50 决策：分别估 $34.42 / **$24.62**。
- 每次 60 决策：分别估 $41.60 / **$29.63**。

因此，**将上下文改为 6 也不能有把握覆盖“40–60 决策完整 debug + 正式 5 次”**。即使每次 40，中心估计也略超过当前余额，而且尚未留重试和下一请求预留额。模型若改变行为，费用可能进一步变化。
